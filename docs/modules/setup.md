# Module: Setup

`pms\extend\plugins\Setup` is the boot lifecycle module. It implements `pms\contract\LifecycleInterface`.

## Entry Point

```php
public static function entry(string $rootPath): void
```

`pms\Boot` passes the project root path when it runs `LIFECYCLE_BOOT`.

## Responsibilities

`Setup` has one current responsibility: initialize plugin autoload files.

It stores the received root path, then calls `initPluginAutoloadFile()`.

## Plugin Root Mounting

`initPluginAutoloadFile()` reads the plugin directory from boot options:

```php
BootOptions::get_extend('plugins', '/plugins')
```

It joins that value with the project root and mounts the result:

```php
Path::mount('pluginsRoot', $pluginDir);
```

After this step, callers can use `Path::getPluginsRoot(...)`. The package includes an IDE-helper method declaration for that dynamic facade method.

## installed.php Handling

`Setup` expects a file at:

```text
<pluginsRoot>/installed.php
```

If the file exists, it is included and treated as the enabled plugin list.

If the file does not exist, `Setup` writes a default PHP file:

```php
return [];
```

## Autoload Inclusion

For each item returned by `installed.php`, `Setup` resolves:

```text
<pluginsRoot>/<item>/autoload.php
```

If the file exists, it is loaded once with `include_once`.

## Important Behavior

- Missing `installed.php` is repaired with an empty list.
- Missing plugin `autoload.php` is silently skipped.
- The enabled list is not generated by directory scanning.
- The returned value of `installed.php` is not deeply validated in this module.
- Plugin classes can still be Composer-autoloadable through the consuming project's `plugins\\` PSR-4 mapping even when a plugin has no `autoload.php`.
